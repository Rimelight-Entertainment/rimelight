## Ways to contribute

There are many ways to contribute to Rimelight Entertainment, and we welcome contributions of any size and contributors of any skill level. This documentation contains all the information you need to get started, and we are happy to help with guidance on PRs, technical writing, and anything you might need through our official channels,.

While we are open to external contributors, most work in our tooling and products is done internally by our team.

If you are interested in working at our company and believe you are qualified, you are welcome to apply for any of our [available positions](https://rimelight.com/company/careers).

## Licensing & Distribution

All software developed by our company is available under one of two distinct licensing models:

- All our plugins and packages are available as [Open Source Software](https://en.wikipedia.org/wiki/Open_source) distributed under the [MIT License](https://opensource.org/license/mit).
  - You are free to use, modify, and embed these into your own projects, commercial or otherwise.
- All our websites, games, and digital products are available as [Source Available Software](https://en.wikipedia.org/wiki/Source-available_software), but with usage restricted under our [custom licensing](https://rimelight.com/legal/licensing).
  - You are restricted from replicating, modifying, or redistributing these, but are free to view, study, and contribute to them through our official channels (if compliant with our [Contributor License Agreement](https://rimelight.com/legal/contributor-license-agreement)).

### Documentation

The Rimelight Entertainment documentation is built with internal tooling and lives within the [rimelight.com](https://github.com/Rimelight-Entertainment/rimelight.com) package as [Markdown](https://daringfireball.net/projects/markdown/) files split between locales.

```text
├── src/
│   └─ content/
│       └─ docs/
│           └─ en/
```

### Internationalization (i18n)

Although we hire dedicated translators to localize our documentation and products, mistakes can happen.

We welcome community revisions and fixes to our translations.

A comprehensive breakdown of missing translations can be found in our [i18n Dashboard](https://rimelight.com/i18n), powered by [Lunaria](https://lunaria.dev).

We currently offer support for the following languages:

- العربية (ar)
- English (en)
- Español (es)
- Français (fr)
- 日本語 (ja)
- 한국어 (ko)
- Português (pt)
- Română (ro)
- 简体中文 (zh_cn)

### Accessibility (a11y)

We continuously audit our products for accessibility compliance, but accessibility is an ongoing effort. We are open to revisions to our accessibility practices to ensure our products are accessible to as many people as possible.

## Local Development

### Website

To begin local development, follow these steps:

<RLASteps>
  <li>
    **Clone the repository:** Clone the
    [`rimelight.com`](https://github.com/Rimelight-Entertainment/rimelight.com) repository from
    GitHub.
  </li>
  <li>
    **Install package managers:** Ensure [pnpm](https://pnpm.io/installation) and [Vite
    Plus](https://viteplus.dev/guide/) are installed.
  </li>
  <li>**Install dependencies:** Run `vp i` in the root of the repository.</li>
  <li>**Run the application:** Run `vpr dev` to start the local development server.</li>
</RLASteps>

## How to submit a contribution

### Submitting a Pull Request

<RLACallout color="warning" variant="soft" title="Commit Message Convention">
    We use [Conventional Commits](https://www.conventionalcommits.org/) for commit messages. Any pull requests that do not follow this convention will be rejected.

    - Use `feat` for new features.
    - Use `fix` for patches and bug fixes.
    - Use `docs` for documentation changes.
    - Use `chore` for maintenance tasks.
    - Use `build` for build system changes.
    - Use `ci` for CI/CD changes.
    - Use `refactor` for code refactoring.
    - Use `style` for code formatting changes.
    - Use `perf` for performance improvements.
    - Use `test` for testing changes.

</RLACallout>

<RLASteps>
  <li>Create a new branch for your feature or bug fix.</li>
  <li>
    Ensure `vpr dev`, `vpr check`, `vpr test`, `vpr build`, and `vpr preview` pass with no errors or
    warnings.
  </li>
  <li>Push your branch and open a pull request against the `main` branch.</li>
</RLASteps>
