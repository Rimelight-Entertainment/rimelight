The `@rimelight/ui` color system is built on a **dynamic, factory-based architecture** with a single source of truth. You define your colors once in `astro.config.ts`, and the library handles the rest — CSS variables, UnoCSS theme mappings, component variants, and safelisting.

Register a new color (like `blurple`) and every supported component automatically gains `solid`, `outline`, `soft`, `subtle`, `ghost`, and `link` variants for it — with no additional code.

## How It Works

### Single Source of Truth: `astro.config.ts`

All color configuration lives in the `ui()` integration's `colors` option as a record of `{ name: { shade: value } }`:

```typescript
// astro.config.ts
ui({
  colors: {
    blurple: {
      "50": "#f4f0ff",
      "100": "#e9e2ff",
      "200": "#d6ccff",
      "300": "#b9a8ff",
      "400": "#967aff",
      "500": "#7146ff",
      "600": "#6222ff",
      "700": "#5512e9",
      "800": "#460ebf",
      "900": "#3b0e9c",
      "950": "#220869"
    }
  }
})
```

From this single declaration, the system:

1. **Emits** `--color-blurple-50` through `--color-blurple-950` as CSS custom properties (via the preset's preflight)
2. **Maps** `bg-blurple-500` → `var(--color-blurple-500)` in UnoCSS's `theme.colors`
3. **Generates** all component compound variants for `blurple`
4. **Safelists** the single class `rl-color-blurple` so UnoCSS compiles it

### UnoCSS Config

No `uno.config.ts` is needed in consuming projects — the `ui()` integration configures UnoCSS with `rimelightUiPreset()` internally, passing your colors automatically.

## Built-in Colors with Default Shade Scales

The library ships with **10 built-in colors** including full 50–950 shade scales. You never need to re-declare them:

| Name         | Purpose                             |
| ------------ | ----------------------------------- |
| `neutral`    | Gray / neutral tones                |
| `primary`    | Brand / primary actions             |
| `secondary`  | Secondary actions                   |
| `info`       | Informational states                |
| `success`    | Positive / success states           |
| `warning`    | Warning states                      |
| `error`      | Destructive / error states          |
| `commentary` | Commentary / annotation context     |
| `ideation`   | Ideation / creative context         |
| `source`     | Source / reference material context |

Override any built-in color by passing its name in the `colors` record with your values. User-supplied shades deep-merge over the defaults:

```typescript
ui({
  colors: {
    primary: {
      "500": "#0064d7", // overrides the default primary-500
      "600": "#0050ac"
    }
  }
})
```

## The `rl-color-{name}` System

Instead of safelisting 13+ utility classes per color (e.g. `bg-blurple-500`, `hover:bg-blurple-600`, `text-blurple-600`, `border-blurple-500/20`, ...), the library uses a **CSS variable indirection** layer:

When the UnoCSS rule `rl-color-{name}` is applied, it sets these CSS variables:

| Variable        | Maps to              | Purpose           |
| --------------- | -------------------- | ----------------- |
| `--rl-bg`       | `--color-{name}-500` | Background color  |
| `--rl-bg-hover` | `--color-{name}-600` | Hover background  |
| `--rl-text`     | `--color-{name}-600` | Text / foreground |
| `--rl-ring`     | `--color-{name}-500` | Focus ring color  |
| `--rl-border`   | `--color-{name}-500` | Border color      |

Component compound variants then reference these variables via arbitrary-value utilities:

```typescript
// In button.theme.ts (simplified)
compoundVariants: [
  ...colors.map((color) => ({
    variant: "solid",
    color,
    classNames: {
      root:
        "rl-color-" +
        color +
        " bg-[var(--rl-bg)] text-white hover:bg-[var(--rl-bg-hover)] focus-visible:ring-[var(--rl-ring)]/50"
    }
  }))
]
```

The safelist shrinks from 13+ entries per color to just **one**: `rl-color-{name}`.

To change which shade is used as the "base" background for all components, you edit the rule in one place rather than every compound variant.

## What Gets Generated

For every registered color, each component variant uses the `--rl-*` variables with variant-specific opacities:

| Variant   | Pattern                                                                                             |
| --------- | --------------------------------------------------------------------------------------------------- |
| `solid`   | `bg-[var(--rl-bg)] text-white hover:bg-[var(--rl-bg-hover)] focus-visible:ring-[var(--rl-ring)]/50` |
| `outline` | `border-[var(--rl-border)]/20 text-[var(--rl-text)] bg-[var(--rl-bg)]/5`                            |
| `soft`    | `text-[var(--rl-text)] bg-[var(--rl-bg)]/10`                                                        |
| `subtle`  | `text-[var(--rl-text)] bg-[var(--rl-bg)]/10`                                                        |
| `ghost`   | `text-[var(--rl-text)] hover:bg-[var(--rl-bg)]/10`                                                  |
| `link`    | `text-[var(--rl-text)] hover:underline hover:decoration-current`                                    |

Usage is identical:

```astro
<RLAButton color="blurple" variant="solid">Click me</RLAButton>
<RLAButton color="blurple" variant="outline">Click me</RLAButton>
<RLAButton color="blurple" variant="ghost">Click me</RLAButton>
```

## Arbitrary Shade Keys

Shade keys are **not limited to 50–950**. The `theme.colors` mapping and CSS variable emission accept any key you provide. This allows non-standard shades like `blurple-374`:

```typescript
ui({
  colors: {
    custom: {
      "374": "#ff3366"
    }
  }
})
```

The library emits `--color-custom-374: #ff3366` and maps `bg-custom-374` → `var(--color-custom-374)`. Components that reference the standard 500/600 shades via `rl-color-custom` will be undefined for this color, but direct utility usage (`bg-custom-374`, `text-custom-374`) works as expected.

## Adding a New Color: Checklist

1. **Add the color record** to `astro.config.ts`:

   ```typescript
   ui({
     colors: {
       mygold: {
         "50": "#fffbe6",
         /* ... other shades ... */
         "950": "#1a1200"
       }
     }
   })
   ```

2. **No other config changes needed** — the `ui()` integration picks up the config automatically.

3. **Restart your dev server** — `astro.config.ts` requires a full restart.

## Theme Awareness (Light / Dark Mode)

Each color can optionally define **mode-specific overrides**. By default, colors are theme-unaware (same in all modes). Add `light`, `dark`, or `flat` buckets to opt in.

### Color Config Format

Colors accept two formats that can be **mixed** within a single entry:

**Flat format** — a base value used in all modes where no mode override exists:

```typescript
ui({
  colors: {
    // Flat: same value in all modes
    blurple: { "500": "#7146ff", "600": "#6222ff" }
  }
})
```

**Mode format** — flat shades at the root serve as the base; `light`, `dark`, and `flat` buckets override specific shades per mode:

```typescript
ui({
  colors: {
    blurple: {
      // Base: used in all modes unless overridden
      "500": "#7146ff",
      "600": "#6222ff",
      // Mode-specific overrides
      "light": { "600": "#7a55ff" }, // only 600 differs in light mode
      "dark": { "500": "#9b7aff", "600": "#b096ff" }
    }
  }
})
```

Each shade is resolved per-mode using this fallback chain:

| Mode       | Fallback order                        |
| ---------- | ------------------------------------- |
| Light      | `light` → flat keys → `flat` → `dark` |
| Dark       | `dark` → flat keys → `flat` → `light` |
| Flat/theme | `flat` → flat keys → `light` → `dark` |

If a shade is missing from all sources for a given mode, it is not emitted (undefined). Defining a single source (e.g. only `dark`) propagates to all modes through the chain.

### Under the Hood

The preset's preflight emits four sets of CSS variables for each color:

```css
:root {
  /* Themed (light mode) */
  --color-blurple-500: #7146ff;
  --color-blurple-600: #6222ff;

  /* Pinned (-f suffix): flat bucket value — never overridden */
  --color-blurple-500-f: #7146ff;
  --color-blurple-600-f: #6222ff;

  /* Pinned (-l suffix): light mode value — never overridden */
  --color-blurple-500-l: #7146ff;
  --color-blurple-600-l: #6222ff;

  /* Pinned (-d suffix): dark mode value — never overridden */
  --color-blurple-500-d: #9b7aff;
  --color-blurple-600-d: #b096ff;
}
.dark {
  /* Dark mode overrides — only the themed var changes */
  --color-blurple-500: #9b7aff;
  --color-blurple-600: #b096ff;
  /* Pinned -f, -l, -d variants are NOT set here — they stay pinned */
}
```

The `rl-color-{name}` rule sets the themed variable plus three pinned variants:

| Variable        | Themed               | Flat pinned       | Light pinned      | Dark pinned       |
| --------------- | -------------------- | ----------------- | ----------------- | ----------------- |
| `--rl-bg`       | `--color-{name}-500` | `--rl-bg-f`       | `--rl-bg-l`       | `--rl-bg-d`       |
| `--rl-bg-hover` | `--color-{name}-600` | `--rl-bg-hover-f` | `--rl-bg-hover-l` | `--rl-bg-hover-d` |
| `--rl-text`     | `--color-{name}-600` | `--rl-text-f`     | `--rl-text-l`     | `--rl-text-d`     |
| `--rl-ring`     | `--color-{name}-500` | `--rl-ring-f`     | `--rl-ring-l`     | `--rl-ring-d`     |
| `--rl-border`   | `--color-{name}-500` | `--rl-border-f`   | `--rl-border-l`   | `--rl-border-d`   |

### Override Classes: `rl-flat`, `rl-light`, `rl-dark`

Each override class swaps the themed `--rl-*` variables to a pinned set:

| Class      | Swaps to         | Use case                         |
| ---------- | ---------------- | -------------------------------- |
| `rl-flat`  | `var(--rl-bg-f)` | Always use the flat bucket value |
| `rl-light` | `var(--rl-bg-l)` | Always use the light mode value  |
| `rl-dark`  | `var(--rl-bg-d)` | Always use the dark mode value   |

```css
.rl-flat {
  --rl-bg: var(--rl-bg-f);
  --rl-bg-hover: var(--rl-bg-hover-f); /* ... */
}
.rl-light {
  --rl-bg: var(--rl-bg-l);
  --rl-bg-hover: var(--rl-bg-hover-l); /* ... */
}
.rl-dark {
  --rl-bg: var(--rl-bg-d);
  --rl-bg-hover: var(--rl-bg-hover-d); /* ... */
}
```

### Component `theme` Prop

Every themeable component accepts a `theme` string prop:

```astro
<!-- Theme-aware: background changes in dark mode -->
<RLAButton color="blurple" variant="solid">Adaptive</RLAButton>

<!-- Flat: same color regardless of mode -->
<RLAButton color="blurple" variant="solid" theme="flat">Flat</RLAButton>
```

The `theme` prop is an opt-out at the usage site. By default, all components are theme-aware when the color provides dark values.

How it works — the component theme adds a single variant:

```typescript
theme: {
  flat: {
    root: "rl-flat"
  }
}
```

The `rl-flat` class (a single UnoCSS rule at `presets/index.ts`) overrides five CSS variables to their `-f` counterparts:

```css
.rl-flat {
  --rl-bg: var(--rl-bg-f);
  --rl-bg-hover: var(--rl-bg-hover-f);
  --rl-text: var(--rl-text-f);
  --rl-ring: var(--rl-ring-f);
  --rl-border: var(--rl-border-f);
}
```

Since every compound variant references these variables (`bg-[var(--rl-bg)]`, `text-[var(--rl-text)]`, etc.), overriding the `--rl-*` chain to the pinned `-f` variant pins **all** color-driven styling at once. One class, zero per-color safelist additions, works for every component and every color.

## Overriding a Built-in Color's Values

To change what `primary` looks like, pass its shades in the `colors` record:

```typescript
ui({
  colors: {
    primary: {
      light: { "500": "#14b8a6", "600": "#0d9488" },
      dark: { "500": "#2dd4bf", "600": "#14b8a6" }
    }
  }
})
```

No CSS files or `@theme` blocks needed.
