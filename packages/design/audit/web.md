## 2. Intents

`INTENTS` (preset.ts:25-34) maps an intent name to a shade for `text`, `bg`, `border` and `ring`. ## 3. How a component's colour is applied

- `color: "auto"` in a theme (for example button.theme.ts:49, badge.theme.ts:42, select.theme.ts:54) makes the resolver append `rl-color-<color>` to the root slot (resolver.ts:400-406). The colour prop defaults to the theme default (for example `primary`).
- The rule at preset.ts:115-130 (`/^rl-color-([\w-]+)$/`) sets, for colour `c`:
  - `--rl-bg` = `var(--rl-c-500)`
  - `--rl-ring` = `var(--rl-c-500)`
  - `--rl-border` = `var(--rl-c-500)`
  - `--rl-bg-hover` = `var(--rl-c-600)`
  - `--rl-text` = `var(--rl-c-600)`
- Components then consume these tokens with arbitrary values, for example `bg-[var(--rl-bg)]/10` (button.theme.ts:34) or `text-[var(--rl-text)]` (badge.theme.ts:33).
- Neutral overrides: compound variants such as button.theme.ts:77-117 and badge.theme.ts:57-91 use intent classes (`text-inverted`, `bg-elevated`, ...) when `color: "neutral"`.
- Safelist: `rl-color-<name>` is safelisted for every palette key (preset.ts:85).

## Notes and gaps

- Hex values are sRGB approximations of OKLCH, computed in the included script. Out-of-gamut cases are clipped and flagged in the ramp tables.
- Heights in section 5 are derived from class names, not from rendered output.
- Shadow and radius values for wind4 defaults were not read from the UnoCSS package and are assumptions (except rounded-md, which the brief specifies).
- Tooltip has no size variant. Tabs and dropdown-menu have no colour variant.
- Not verified: the rendered font families and whether `fontsource` fetches succeed at build time.
