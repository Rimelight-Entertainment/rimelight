# RFC: Email-Safe UI Components

- **Status**: Draft
- **Author(s)**: Rimelight Team
- **Created**: 2026-07-25
- **Last Updated**: 2026-07-25

---

## 1. Summary

Add a dedicated email component family to `@rimelight/ui`. These components should follow Rimelight's existing component API and design-token conventions while producing static, email-safe HTML with inline styles.

The initial consumer is the authentication email system in `packages/rimelight.com`, including `SignupNotificationEmail.astro`.

## 2. Motivation

Rimelight email templates are now Astro components, which gives them HMR previews and a shared source of truth for rendering and sending. General UI components such as `RLAButton` are not directly email-safe because they depend on generated CSS classes and may include browser behavior.

Email authors should still receive familiar Rimelight DX without needing to manually recreate buttons, typography, spacing, and layout for every template.

## 3. Goals

- Provide reusable email-safe Astro components in `@rimelight/ui`.
- Preserve familiar props such as `color`, `variant`, `size`, `href`, `label`, and slots where appropriate.
- Render static HTML only.
- Generate critical styles as inline `style` attributes.
- Reuse Rimelight design tokens where they map safely to email clients.
- Support Astro preview pages with HMR and server-side email rendering.
- Make unsupported behavior obvious through types and documentation.

## 4. Non-Goals

- Making interactive web components work inside email.
- Supporting client-side JavaScript, hydration, loading states, dialogs, popovers, or tooltips.
- Guaranteeing identical rendering across all email clients.
- Reusing every prop from the normal UI components.
- Adding a general-purpose email rendering service in this RFC.

## 5. Proposed Component Family

```text
packages/ui/src/components/email/
  RLEmailLayout.astro
  RLEmailText.astro
  RLEmailHeading.astro
  RLEmailButton.astro
  RLEmailDivider.astro
  RLEmailImage.astro
```

The `RL` prefix distinguishes email components from the existing `RLA`, `RLV`, and `RLS` framework components while keeping the package naming convention consistent.

## 6. Example API

```astro
---
import RLEmailButton from "@rimelight/ui/components/email/RLEmailButton.astro"
---

<RLEmailButton href={signInUrl} color="primary" size="md">
  Sign in
</RLEmailButton>
```

The component would produce a normal link with inline styles:

```html
<a
  href="https://rimelight.com/auth/sign-in"
  style="display:inline-block;background:#6d4aff;color:#fff;padding:12px 20px;border-radius:6px;text-decoration:none"
>
  Sign in
</a>
```

## 7. Styling Strategy

Email components must not depend on generated UnoCSS/Tailwind classes for essential presentation. They should resolve theme values to inline styles during Astro rendering.

Allowed styling sources:

- Inline styles generated by the component.
- Simple email-safe HTML attributes such as `width`, `align`, and `role` where needed.
- A small layout stylesheet in preview-only components.

Avoid relying on:

- External stylesheets.
- Utility classes being available in the recipient's email client.
- CSS variables.
- Advanced selectors, animations, or layout features with inconsistent client support.

Design tokens should be shared with the normal UI library, but email components may use a compatibility mapping when a token or CSS feature is not reliable in email clients.

## 8. Rendering and Preview

Email templates remain Astro components:

```text
src/components/email/SignupNotificationEmail.astro
```

Development previews import those components directly through Astro pages, preserving HMR. Sending renders the same component through Astro's server container and passes the resulting HTML to `sendEmail`.

The email component must not depend on `Astro.url`, request-only data, browser globals, or client-side scripts unless those dependencies are explicitly supplied by the caller.

## 9. Compatibility Rules

Email-safe components may support:

- Static text and links.
- Absolute URLs.
- Images with explicit dimensions and alt text.
- Table-based layout where client compatibility requires it.
- Limited variants and sizes.

They must reject or omit:

- `loading` and `loadingAuto` behavior.
- Event handlers.
- Hydration directives.
- Interactive state.
- Components whose output requires JavaScript.

`RLEmailButton` should use an `<a>` element when `href` is provided. A `<button>` should not be the default email action element because email clients do not provide normal application button behavior.

## 10. Migration Plan

1. Add the email component primitives to `@rimelight/ui`.
2. Add component documentation and email-client usage guidance.
3. Migrate `SignupNotificationEmail.astro` to `RLEmailButton` and other primitives.
4. Migrate verification and password-reset templates.
5. Remove duplicated raw markup and confirm preview/send output use the same components.
6. Add snapshot tests for generated HTML and inline styles.

## 11. Validation

- Astro type checking passes for the UI package and `rimelight.com`.
- Preview pages render correctly in development with HMR.
- Generated HTML contains no client scripts or hydration directives.
- Required visual styles are inline.
- Links are absolute and preserve their intended destinations.
- HTML is checked with an email-compatible markup validator.
- Representative output is tested in major email clients or a service such as Email on Acid/Litmus where available.

## 12. Open Questions

1. Should email components use a separate `RLEmail` prefix or an `RLAEmail` namespace?
2. Should the library provide automatic CSS inlining for advanced composed templates?
3. Which email clients are part of the minimum support matrix?
4. Should components use table markup by default for layout primitives?
5. Should email-safe tokens be a separate theme or a compatibility layer over the existing theme?
